Problem & context

Thesis

Objective: high-quality decisions at high velocity. Bottleneck: human cognition at design/spec time. The format of the doc is the lever — restructure it for cognition, not for the writer's convenience.

Today the brainstorming and planning skills produce markdown. Markdown is excellent for AI agents (token-efficient, parseable, diff-friendly) and for terminal reading. But the human-review path — where the high-stakes decisions actually get made — runs through long-form prose that takes ~10–15 minutes per spec to absorb before a confident decision is possible.

Premise stack

  1. Quality decisions require deep understanding of the scenario.
  2. Deep understanding from a markdown wall is slow, tedious, manual, and high cognitive-load.
  3. Across many specs, this produces cross-pollination errors — context from doc N bleeds into the decision on doc N+1.
  4. Long reads cause context rot mid-decision: by the time you reach the asks, you've forgotten the constraints.
  5. Context switching is brutal. Past 2–3 concurrent specs, decision quality degrades fast.
  6. Therefore: optimize the doc format around the bottleneck — human cognition at decision time.

The win isn't prettier docs. It's amortized comprehension — the cost of structuring the doc for cognition (visual hierarchy, surfaced decisions, diagrams in place of prose, the 5-minute brief at the top) is paid once by the agent producing it, and that one-time investment gets paid back across every reader and every re-read. A 12-minute prose wall becomes a 2-minute scan that yields ~80% of the decision-relevant signal; the remaining 20% sits in clearly-labeled deeper sections, drilled into only when the decision needs it.

Etymology — why this name

Amortization (finance / CS amortized analysis) — spreading a high one-time cost across many small increments so the average cost per increment is low. Comprehension — grasping the meaning of complex information. Combined: the doc pays the structuring cost once, and every reader after that scans cheaply. Mental effort — the real cost — gets broken down over time and across people, the same way a mortgage breaks a $500K cost into 360 affordable monthly payments.

Without amortization, every reader pays the full 12-minute cost from scratch — and across many concurrent docs, that cost compounds into the bottleneck the doc itself was meant to remove.

Honest cost

HTML output runs ~2–4× more output tokens and ~2–4× longer to generate than the MD equivalent (per Thariq's Unreasonable Effectiveness of HTML field notes). The amortized-comprehension thesis is that this one-time author-side cost is dwarfed by the reader-side savings that compound across every reader and every re-read. We accept the trade because reads outnumber writes, and reader cognition is the bottleneck — not author throughput.

Approaches considered

Three variants on each of two axes (HTML's role, and how it's triggered) were explored. Below are the dominant variants and why we picked the recommended one.

Approach Pros Cons Concession / verdict
A. HTML replaces MD
Skills write rich HTML directly. CLAUDE.md overrides their MD default.
Chosen 		Single canonical artifact. No sync overhead. Doc-reviewer already supports .html. Highest-priority instruction layer (CLAUDE.md) cleanly overrides skill defaults. Harder to PR-diff than MD. Existing MD convention in CLAUDE.md needs replacement. Browser needed to view (cheap concession). Restrict to human-review docs only — AI-execution docs stay MD. PR diff issue is real but bounded; mitigate later with rendered-preview tooling.
B. HTML supplements MD
MD stays canonical. HTML is generated from MD on demand.
Rejected 		Zero workflow disruption. MD stays diffable. Doc-reviewer keeps working on MD as today. Two artifacts to sync. Generation step required (when? by whom?). Rich elements (callouts, decision cards) don't have a natural MD source — they'd need extension syntax that defeats the simplicity premise. The richness we want isn't translatable from MD without a new authoring layer. That's just HTML with extra steps.
C. Hybrid per-doc choice
Author flags HTML or MD per doc.
Rejected as default 		Right tool per job. Maximum flexibility. Most cognitive overhead at the moment of authoring. Easy to drift. Defeats "high velocity" — author has to think about format before content. Rolled into A as the override mechanism (/p2e-html · /p2e-md) rather than the default policy. You get the flexibility without the per-author decision tax.
D. No skill — just prompt for HTML each time
Per Thariq's Unreasonable Effectiveness of HTML essay: skip the skill, just say "make an HTML file" when you want one.
Rejected 		Zero infrastructure. Maximum agent freedom on visuals. Works fine for one-offs viewed in a generic browser. (1) Inconsistent docs across the corpus — every doc re-derives the design system, structure, and section shapes; the reader's "amortized comprehension" never accrues across docs. (2) Comment-anchor breakage — doc-reviewer threads anchor on element IDs/structure; if those drift between regenerations, comments come unstuck. (3) Doesn't auto-steer superpowers skills — brainstorming, writing-plans, executing-plans, requesting-code-review etc. are the workhorse here, and they default to MD without active intervention. "Just prompt" doesn't fix the default; the skill does. Thariq's "just prompt" works because his target is one-off general HTML viewed in a browser. Ours has constraints he doesn't: doc-reviewer's commenting + outline rail are the review surface, and superpowers skills are the production surface. The skill exists to steer those skills consistently and to produce stable structure the comment system can anchor to.

Recommended approach

1

CLAUDE.md rule

~/.claude/CLAUDE.md

A new Doc Output Conventions section replaces the existing Markdown Conventions section. Contains the audience classification table and override syntax. Highest-priority instruction layer — wins over any baked-in MD default in skills.

2

Companion skill

bchoor/p2e-plugin · cross-tool

Ships in the bchoor/p2e-plugin family alongside the existing /p2e-* workflows. Carries an opinionated template + design system: ready-made theme tokens, component library (callouts, cards, tables, premise/step lists), layout templates, pedagogical-strategy menu, and the doc-reviewer compatibility rules. Authored once for codex / claude / cursor / opencode — same SKILL.md surfaces consistently in each runtime.

3

Override + convert commands

bchoor/p2e-plugin · /p2e-{html,md,md-to-html}

Three thin slash commands in the same plugin. /p2e-html forces HTML on the next doc-producing skill; /p2e-md forces MD; /p2e-md-to-html converts an existing .md doc to a rich .html applying the full design system. Each loads override instructions into the next turn's context — no wrapping logic.

Template anatomy — what makes the HTML "rich"

Every element here serves the cognitive-amortization thesis and is doc-reviewer-compatible (no JS, no sticky, no in-doc nav, single linear scroll).

Plain header — title, status pill, hash/date/owner at the top. Not sticky.
5-min brief first — TL;DR + one inline-SVG diagram. Above the fold, before anything else.
Decision cards — open questions surfaced as their own section, isolated from analysis.
Color-coded callouts — sky=info, amber=decision, emerald=recommendation, rose=risk. Consistent across docs.
Comparison tables — pros/cons/verdict side-by-side, not buried in prose.
Inline SVG diagrams — architecture, flow, sequence — rendered statically, no JS.
Numbered premise/step lists — explicit P1/P2 or 1/2/3 markers via CSS counters.
Hand-tuned typography — Inter for body, JetBrains Mono for code, scoped CSS in a single <style> block.
Stable element IDs — every section id stays stable so /doc-reviewer-review can anchor comments.
Doc-reviewer rail handles outline — never duplicate it in the artifact.

Skill quality bar — opinionated, not a sandbox

The skill exists so the agent never spends thinking tokens on visual implementation. The agent picks pedagogy; the skill provides the rendering. This is the pattern Thariq endorses in his HTML-effectiveness essay: "create a single design system HTML file by pointing Claude at your codebase. You can then use that design system file as a reference for other html files." Our template.html in the skill is exactly that file; this design.html follows it.

Agent does

Choose which pedagogical strategy fits the content (premise stack vs comparison table vs decision cards vs flow diagram). Write the prose. Decide what belongs above the fold.

Agent does NOT

Pick colors, fonts, spacing, or component layouts. Re-derive callout/card/table CSS. Decide whether to use Tailwind. Re-discover the doc-reviewer compatibility rules. All of this is provided.

Theme tokens — palette, type scale, radii, spacing — drop-in CSS variables ready to copy into any new doc.
Component library inline — copy-paste blocks for cards, decision cards, callouts, tables, premise lists, step lists, three-pieces grids, anatomy grids.
Layout templates — top-of-doc 5-min-brief shape, decisions section shape, recommendation section shape, deferred-list shape.
Strategy menu — for each cognitive task (compare options, surface premises, walk a flow, show before/after), the skill names the visual strategy and points to the component to reach for.

How the override commands work

Each command is a thin skill that loads instructions into context for the next doc-producing skill in the same turn. No wrapping logic, no per-skill bindings.

# Force HTML on a doc that would otherwise default to MD:
/p2e-html  /superpowers:brainstorming  redesign the comments rail

# Force MD on a doc that would otherwise default to HTML:
/p2e-md  /superpowers:brainstorming  trivial config-only ADR

# Convert a legacy markdown spec to a rich HTML doc on demand:
/p2e-md-to-html  docs/feat-comments-rail-redesign/spec.md
